# Trevra GTM App — Simplicity Audit: Prioritized Findings for Product Owner

_Synthesized from 8 independent reviewer clusters, each auditing one page group against the same checklist: smart defaults, no dead-end gated wizards, no surprise mount-time fetches, fuzzy/forgiving matching, disabled controls that explain themselves, and progressive disclosure._

## Through-line

The dominant pattern across almost every page is the same: **screens default to showing everything at once instead of the one thing the operator came to do.** Config panels, analytics breakdowns, and secondary flows render fully expanded on mount — often on pages that already know a lighter pattern works (each cluster has at least one `<details>`/toggle example elsewhere in the same file it fails to reuse). A second, smaller theme sits underneath it: several real capabilities (edit a research source, withdraw a pending invite, cancel an invitation, see the campaign you just opened) exist in the backend or SDK but have no wire-up to a control an operator can actually press — the opposite failure from option overload, but the same root cause of not finishing the "reachable, but not in your face" design halfway through.

## Appendix — Full findings by page cluster (verbatim)

### Loop (`/loop`, `/loop/cost`)

**1. Progressive disclosure / option overload — duplicate content shown by default**

- Location: `src/client/views/LoopView.tsx:113-120` (stages[1] 'reach' tile) and `L236-247` (Metric 'Going out')
- Problem: The exact same number (`queued = loop.planned + loop.exported`) is rendered twice on the page under two different labels: the 'Reach' stage tile shows it as 'queued', and the 'Going out' metric card a few lines below shows the identical `String(queued)` value again. Two visually distinct components spend space repeating one figure instead of each carrying unique signal, which makes the always-on dashboard feel denser than the actual amount of information it conveys.
- Proposal: Drop the duplication: either remove the 'Going out' metric card (the stage tile at the top already gives this number at a glance, and the daily-limit detail could move into the stage tile's `unit` text), or repurpose the metric card to show something the stage tile doesn't — e.g. a breakdown of invites vs. follow-ups queued — so the two panels stop saying the same thing twice.
- Severity: medium

**2. Progressive disclosure / option overload — duplicate data at silently different windows**

- Location: `src/client/views/LoopView.tsx:78` (hardcoded `getLinkedInAnalytics(7)`) and `L249-260` (Metric 'Waiting on a reply' / 'Accepted / replied') vs. `L296` `<LinkedInFunnel />` which mounts its own independent `useOutreachAnalytics()` hook (`src/client/LinkedInAnalyticsScreen.tsx:72-97`, `DEFAULT_WINDOW_DAYS=30`) and its own WindowChoice control (7/30/90)
- Problem: The Loop page shows 'sent / accepted / replied' twice: once in the metrics-grid, permanently fixed to a 7-day window fetched once on mount, and again a few hundred pixels below inside `<LinkedInFunnel />`'s FunnelBars, which defaults to a 30-day window and lets the operator change it independently via its own picker. The two windows are decoupled — moving the funnel's picker to 90 days never updates the metric cards above, so 'Accepted / replied' up top and 'Accepted' in the funnel below can legitimately disagree at a glance, with only a small 'Last 7 days' caption to explain why. The same file's own doc-comment in `LinkedInAnalyticsScreen.tsx` (L21-28) explicitly calls this exact failure mode a bug elsewhere ('how a founder concludes the product cannot add up') but the mismatch still exists between LoopView's metrics-grid and the LinkedInFunnel it embeds.
- Proposal: Either delete the 'Waiting on a reply' and 'Accepted / replied' metric cards from the metrics-grid (the funnel below already covers Sent/Accepted/Replied, with a real, user-controlled window picker instead of a silently fixed one), or lift the funnel's `days` state up and pass it into both the metric-grid calculation and `<LinkedInFunnel days={days} onDaysChange={...} />` so the two can never show conflicting numbers for the same window.
- Severity: high

**3. Progressive disclosure / option overload — same fact stated three times by default**

- Location: `src/client/views/LoopView.tsx:226-231` (loop-block CTA), `L261-267` (Metric 'Waiting on you'), `L299-330` (recommendations-panel 'What needs you')
- Problem: When there is at least one run waiting for approval, the operator is told so three separate times in the default render before reaching any new information: the loop-block banner ('{n} runs need your approval.' / 'Open ledger'), the 'Waiting on you' metric card ('Approval required in Ledger'), and the full 'What needs you' panel, which repeats 'n job(s) need approval.' in its own banner before finally listing the per-run deep links. All three render unconditionally and simultaneously — there is no toggle collapsing any of them.
- Proposal: Keep the loop-block CTA (it's the single primary next-action surface the page is built around) and the per-run deep-link list (it's the one part with unique value), but cut the repeated banner sentence out of the recommendations-panel — just keep its heading ('What needs you') plus the run buttons — so the count is stated once at the top and acted on once at the bottom, not restated a third time in between.
- Severity: medium

**4. Progressive disclosure — operational/debugging detail shown by default on a cost-overview page**

- Location: `src/client/views/LoopView.tsx:643-663` (run-facts: Agent runs / Completed / Failed / Stopped / Still running, inside LoopCostView's 'Sent' section)
- Problem: LoopCostView is already the on-demand 'details' surface reached via 'View details' from `/loop`, which is the right place for depth — but even there, the 'Sent' section always renders a 5-number agent-run execution breakdown (total/completed/failed/stopped/running) unconditionally alongside the actions-sent table. That's job-diagnostic information for someone debugging failed runs, not what an operator checking 'what did this cost, what did it produce' is looking for, and the page already links to the Ledger (L697-706) as the dedicated surface for run-level diagnostics.
- Proposal: Collapse the 'Agent runs' run-facts block behind an on-demand 'Show run status' disclosure within the Sent section (or drop it from this view entirely and rely on the existing 'Open the run ledger' link at the bottom of the page), leaving the always-visible content limited to the actions-sent table that answers the section's own stated question.
- Severity: low

### Outreach: accounts, activity, leads (`/outreach/accounts`, `/outreach/activity`, `/outreach/leads`)

**1. Smart defaults (derivable value left blank)**

- Location: `src/client/LinkedInAccounts.tsx:2656` (`const [key, setKey] = useState(...)`) and `:2741-2762` (Name and Short key fields in AddAccountForm)
- Problem: For every account after the first, the 'Short key' field starts blank (`useState(existingKeys.length === 0 ? OWNER_ACCOUNT_KEY : '')`) and must be hand-typed by the operator even though it is fully derivable from the 'Name' field sitting directly above it in the same form — the key is just a slugified version of the same string (letters/digits/dash/underscore, per `ACCOUNT_KEY_PATTERN` at line 91). The operator has to invent a second identifier for the thing they just named, with no live feedback until submit-time validation (`draftToPatch`/pattern mismatch) or a 'you already have an account with that key' error.
- Proposal: Auto-fill Short key as a live slug of Name (lowercase, strip/replace anything outside `[A-Za-z0-9_-]`, truncate to 64 chars, dedupe against `existingKeys` by suffixing -2/-3 on collision) as the operator types the Name — the same 'generated value that stays editable' shape this codebase already uses for the lead-search URL field (`searchUrlForKeywords` + `urlDirty`/'Edit' toggle in `LinkedInLeads.tsx`). Keep the field visible and editable so a deliberate custom key is still one click away, matching the existing url-edit pattern.
- Severity: high

**2. Progressive disclosure / option overload**

- Location: `src/client/LinkedInLeads.tsx:620-706` ('How many new leads a day' section, incl. Save limit button) and `:224` (`getLinkedInLeadAllowance` fetched unconditionally inside `load()`)
- Problem: A full rate-limit configuration panel — numeric input, two stat tiles (collected today / still allowed), explanatory hint, and a Save button — is rendered in full on every visit to `/outreach/leads`, sitting between the primary 'Find people' action and the Sources list, and its backing data (`getLinkedInLeadAllowance`) is fetched on every mount. Most operators set this ceiling once and never revisit it, yet it always carries the same visual weight as the search-building panel that is the page's actual primary action.
- Proposal: Collapse this into an on-demand disclosure (the codebase already has the pattern: `<details>`/'Change name, hours and limits' in `LinkedInAccounts.tsx`, and 'Next LinkedIn background activity' in the same file) that shows just the current limit as one line by default (e.g. 'Up to 200 new leads/day · edit') and only renders the full editor — and only fetches `getLinkedInLeadAllowance` — once expanded.
- Severity: medium

**3. Progressive disclosure / option overload**

- Location: `src/client/LinkedInAccounts.tsx:2535` (`<ProxyField .../>` call inside ScheduleFields, used unconditionally by both AddAccountForm and EditAccountForm)
- Problem: ProxyField (an input plus multi-paragraph explanation of http/https/socks5 proxy routing) is rendered unconditionally at the end of ScheduleFields for every account add and edit, even though the component's own doc comment says outbound-proxy routing 'is not the norm... Leave it empty unless you genuinely have a second line to route through.' In AddAccountForm specifically it is not gated behind any disclosure at all, so a first-time operator adding an account sees it fully expanded alongside the working-hours picker and four daily-limit fields — a field the code itself says almost nobody should touch, given equal billing with fields everyone must set.
- Proposal: Wrap ProxyField in its own on-demand `<details>` ('Route this account through a proxy'), matching the pattern this same file already applies to EditAccountForm itself and to the maintenance schedule. No new fetch is needed either way since the value comes from the already-loaded `account.proxy` — only the default visibility changes.
- Severity: medium

**4. Disabled controls explain themselves**

- Location: `src/client/LinkedInLeads.tsx:689-701` (Save limit button in the daily lead limit panel)
- Problem: The Save limit button is disabled under three conditions — lead sourcing is off, a save is already in flight, or `capDraft === String(allowance.limit)` (nothing has changed) — but only the first is explained anywhere on screen (the 'Lead sourcing is unavailable right now' banner above). When the button is grey because the typed number already matches the stored limit, there is no adjacent text or title saying so; it just looks inert, the exact 'sitting greyed out' pattern the checklist calls out.
- Proposal: Add a one-line adjacent note for the unchanged-value case, e.g. small text next to the button reading 'Already saved' or swap the button to a brief 'Saved' checkmark state when `capDraft === String(allowance.limit)`, consistent with how this same file names other disabled reasons in visible copy (the sourcing-off banner, the proxy-failure sentence in ProxyField).
- Severity: low

### Outreach: legacy campaigns + inbox (`/outreach/campaigns`, `/outreach/inbox`)

**1. Fuzzy/forgiving matching**

- Location: `src/client/LinkedInCampaigns.tsx:432-448` (MERGE_TOKEN / unknownMergeFields), enforced at `:1315-1320` and `:1418-1423`, rendered at ~`:2870-2880`
- Problem: `LINKEDIN_MERGE_FIELDS` is exactly `firstName, lastName, company, jobTitle` (`src/client/api.ts:943-948`). `unknownMergeFields` matches a template's `{{token}}` tokens against that list with a plain `fields.includes(match[1])` — case-sensitive, no separator normalization. A completely natural slip like `{{FirstName}}`, `{{first_name}}`, `{{Company}}`, or `{{job_title}}` is treated as a wholly unknown field. Both Create campaign and Save sequence hard-block on it: 'Remove the merge fields Trevra does not accept: {{FirstName}}.' with no hint of the obvious near-miss, so the operator has to spot the typo themselves after writing (possibly) six steps.
- Failure scenario: An operator writes a DM step copy with `{{Company}}` (capitalized, as most people naturally would in a sentence). Save is blocked with 'Remove the merge fields Trevra does not accept: {{Company}}.' — nothing on screen says the accepted spelling is `{{company}}`, so they have to guess or hunt the merge-field legend at the bottom of the page.
- Proposal: Case/separator-normalize candidate tokens before declaring them unknown, and when a rejected token is a near-miss (case-only or edit-distance <=2 of an accepted field), surface 'Did you mean {{firstName}}?' inline on the same warning line, optionally with a one-click fix. Keep the outgoing bytes exact-match — only the suggestion is fuzzy.
- Severity: medium

**2. Disabled controls explain themselves / consistency**

- Location: `src/client/LinkedInCampaigns.tsx:2112,2133,2149,2274,2297` (kind/horizon/format/tone/inviteNote all `disabled={Boolean(boundId)}`) vs `:2182-2246` (ICP role, Segment, Pain, Offer name, Offer URL, What it does, Why it works, Proof — none disabled)
- Problem: When a campaign is already bound (boundId set), `saveSequence()` posts only `orderedSteps()` — the brief's ICP/offer fields are never sent to the server and have zero effect on the open campaign. The screen correctly disables the sibling controls in the exact same fold (action type, spread, export format, tone, 'no note' checkbox) to signal 'this is inert now,' but leaves the eight ICP/offer/proof inputs fully interactive with no disabled state and no per-field note. Only a general paragraph at the top of the (collapsed, nested) fold hints at this, and it's easy to miss since it doesn't call out which of the many controls below it are affected.
- Failure scenario: An operator reopens an existing campaign to fix a wrong offer description, types a corrected 'What it does' sentence into the still-editable field, clicks 'Save sequence', and sees 'Sequence saved and re-planned' — nothing tells them the offer text they just edited was silently discarded, because Save only ever posts the step list.
- Proposal: Give these eight fields the same `disabled={Boolean(boundId)}` treatment as their siblings in the same section (Action type, Spread, Format, Tone, no-note checkbox), or render them as plain read-only text with the same 'read back from the run this campaign was planned with' framing already used elsewhere on this screen.
- Severity: medium

**3. Smart defaults**

- Location: `src/client/LinkedInCampaigns.tsx:830` (`const [name, setName] = useState('')`), `:948` (startNew), `:1828-1833` (Campaign name input)
- Problem: Every new campaign's name field starts (and resets, via startNew) as an empty string with only a placeholder example ('Q3 RevOps founders'); nothing derives a starting name. This is inconsistent with the rest of the app, which already treats auto-naming as the right default: `LinkedInLeads.tsx` explicitly relies on an 'auto-generated name' for saved lead lists, and `App.tsx`'s API-token flow calls out 'Asking a founder to invent a name before they can [proceed]' as friction it deliberately avoids by auto-naming.
- Failure scenario: An operator who just used 'Draft with AI' or a template — i.e. did everything needed to create the campaign — still can't click Create: the name field is blank, so create() refuses with 'A campaign needs a name and at least one person to reach,' forcing them to stop and invent a label before they can proceed.
- Proposal: Seed `name` with a derivable, fully-editable default the moment domain/targets exist, e.g. `${domain || 'New'} — ${new Date().toLocaleDateString()}` or a running 'Campaign N' counter off `campaigns.length`, matching the auto-name-then-let-them-rename pattern already used for lead lists.
- Severity: low

**4. Smart defaults**

- Location: `src/client/LinkedInCampaigns.tsx:831` (`const [domain, setDomain] = useState('')`), `:948` (startNew clears it again)
- Problem: `domain` is required before 'Draft with AI' will run (draftSequence blocks with an error if it's blank) but is never remembered anywhere — not across `startNew()` within the same session, and not persisted to localStorage the way the active seat/account choice already is (`useActiveSeatKey`). An operator's own company domain essentially never changes between campaigns, yet every single new campaign — including a second one built five minutes after the first, in the same session — starts with a blank domain field.
- Failure scenario: An operator builds two campaigns back-to-back for different target lists on the same domain. After the first campaign is created and they click 'New campaign', the domain field is empty again and they have to retype `trevra.com` (or whatever it is) before Draft with AI will run a second time.
- Proposal: Persist the last-entered domain the same way the active account is persisted (localStorage/event, mirroring `useActiveSeatKey`), and prefill `domain` from it on mount and after `startNew()`, while keeping it fully editable.
- Severity: low

**5. Progressive disclosure / option overload**

- Location: `src/client/LinkedInCampaigns.tsx:1631` (`{campaigns.length > 0 && <LinkedInCampaignBreakdown />}`); fetch source: `src/client/LinkedInAnalyticsScreen.tsx:72-97` (`useOutreachAnalytics` fires `getLinkedInAnalytics(days)` on mount)
- Problem: The instant a workspace has any campaigns, opening this page unconditionally renders — and fetches data for — a full 'By campaign' analytics table (a window-choice filter plus a 9-column table: Campaign, Status, Planned, Exported, Sent, Accepted, Replied, Declined, Acceptance) sitting between the campaign list and the actual campaign-detail/builder panel below it. This page's own banner frames it as 'the advanced path' for assembling and approving a sequence; reviewing historical acceptance/reply performance is a different task that most visits don't need, and it both triggers an unrequested network read and pushes the primary builder further down the page.
- Failure scenario: An operator with a handful of existing campaigns opens `/outreach/campaigns` just to build a new sequence. Before reaching the 'New campaign' form they scroll past a full performance table (and its own loading spinner while `getLinkedInAnalytics` resolves) that has nothing to do with the task they're there for.
- Proposal: Collapse the breakdown behind an on-demand 'Show performance' toggle next to the 'Sequences you have built here' heading — matching the disclosure pattern already used elsewhere on this same page (the 'Fine-tune the brief' fold, the lead-source picker) — so `getLinkedInAnalytics` fetches nothing until the operator explicitly asks for it, with the full table and window picker unchanged once opened.
- Severity: low

### Outreach: manager read/analytics/safety (manager operating view)

**1. Smart defaults (derive from what the operator already told the page)**

- Location: `src/client/LinkedInManagerRead.tsx` lines 861, 869, 1299-1300, and 1534-1546 (openCampaignId / campaignFilter state and the Results filter `<select>`)
- Problem: Expanding a campaign card sets `openCampaignId` (line 861, toggled at line ~1300) but the Results panel's own `campaignFilter` (line 869, the `<select>` at line 1538) is a completely separate piece of state with no effect linking the two. An operator who clicks open "Campaign X" to inspect its members, then scrolls down to Results expecting to see Campaign X's numbers, instead sees the workspace-wide "All campaigns" aggregate and must manually reselect "Campaign X" from the dropdown. This is a real inconsistency within the same file: the sibling `seatFilter` state (line 870) explicitly derives its initial value from `activeSeatKey` and writes back to it via `pickSeatFilter` (lines 1105-1108), with a code comment explaining exactly why that derivation matters ("choosing an account to read results for is the same act as choosing the account the inbox and queue are showing") — the same reasoning was never applied to the campaign axis.
- Proposal: When a campaign card is expanded (`openCampaignId` becomes non-empty), set `campaignFilter` to that campaign id too (and clear it, or leave it, when the card is collapsed — whichever matches the seat-filter precedent). This makes the Results panel answer "how is the campaign I just opened doing" without an extra manual selection, mirroring the existing seat-filter pattern in the same component.
- Severity: high

**2. No surprise fetch producing a misleading unrelated error banner**

- Location: `src/client/LinkedInSafety.tsx` lines 862-895 (useAccountTruth's reload) and lines 1007-1015 (the configError banner)
- Problem: `useAccountTruth.reload()` wraps three different reads in one try/catch: `getLinkedInManagerSeats()` + `getLinkedInManagedCampaigns()` (the operator's actual account settings) on line 864, and then, in the same try block, a per-secondary-seat `getLinkedInActions(...)` call (line 878) that only enriches the panel with a 24h usage count. `setAccounts(rows)` and `setCampaigns(managed)` (lines 865-866) already ran and succeeded before that second block executes. If a single secondary seat's `getLinkedInActions` call throws (e.g. a transient failure), the whole function falls into the catch at line 894 and sets the same generic error regardless of which read actually failed. That error is rendered at lines 1007-1015 as "Your own settings for these accounts could not be read... the working days, the hours and the four per-account ceilings you set are missing" — even though those settings were read successfully and are currently displayed correctly; only an incidental usage-count enrichment for one seat failed.
- Proposal: Wrap the per-seat `getLinkedInActions` loop in its own try/catch (mirroring the pattern `LinkedInManagerRead.tsx`'s `load()` already uses for its per-campaign and per-seat reads, where each item's failure is caught individually and falls back to omitting that entry) so a failed usage-count read leaves `usage` for that seat absent without ever claiming the operator's settings could not be read.
- Severity: high

**3. Progressive disclosure / option overload**

- Location: `src/client/LinkedInManagerRead.tsx` lines 1519-1678 (the "Results" panel: 10 always-visible stat tiles plus the full A/B "Message versions, side by side" breakdown) versus lines 1843-1849 (the "Campaign inputs" section, correctly collapsed behind `<details>`/`<summary>`)
